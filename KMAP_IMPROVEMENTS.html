KMaP library improvement roadmap

KMaP has a promising architecture and unusually broad target support. The highest-leverage next step is to harden the production raster path—especially tile scheduling, lifecycle management, caching, and tests—before expanding the feature set.

Highest priority

1

Fix tile-loader lifecycle and backpressure High

Evidence: TileRenderer.kt uses three unlimited channels, starts one coroutine for every requested tile, and launches its processor with Dispatchers.Default + SupervisorJob().

This can cause fast camera movement to accumulate obsolete requests, unbounded network and decoding concurrency, growing memory use, and work that survives after the owning Compose scope is disposed.

Kotlin explicitly documents that passing a new Job to launch breaks structured concurrency. See the Kotlin coroutine documentation.

Recommended changes:

  • Use a bounded request queue.
  • Limit concurrent workers, initially to a small fixed number such as 4–8.
  • Prioritize tiles nearest the viewport center.
  • Cancel requests that are no longer near the viewport.
  • Key requests by normalized TileSpecs to deduplicate work.
  • Inherit the provided coroutine scope lifecycle directly.
  • Define an explicit retry and backoff policy.
2

Improve cache behavior High

Evidence: CanvasEngine.kt keeps the last inserted tiles in a list, permits duplicate entries, rebuilds maps and lists frequently, and does not update recency when a tile is read.

Replace the list with a small LRU cache keyed by TileSpecs. This would provide:

  • O(1) lookup and deduplication.
  • True least-recently-used eviction.
  • Memory-based limits in addition to tile-count limits.
  • An injection point for persistent or offline caches.
  • Cache statistics for performance diagnostics.
3

Add tests around the production path High

KMaP has 98 JVM tests, which is a solid base, but they are concentrated in vector parsing and styling. The production raster path has little direct coverage.

Add behavioral tests for:

  • MapState coordinate round trips.
  • Zoom, rotation, density, and map-boundary behavior.
  • Visible-tile selection.
  • Horizontal wrapping versus vertical bounds.
  • Request deduplication, prioritization, and cancellation.
  • Parent and child fallback rendering.
  • Cache eviction and reuse.
  • Gestures and transformations centered on a screen point.
  • Cancellation of work when the owning scope ends.

Move platform-independent cases into commonTest so they run across supported targets. Kotlin recommends common tests for shared code and target-specific tests where behavior differs. See the Kotlin Multiplatform testing guide.

Release and API quality

4

Add pull-request CI

The repository automates publishing and documentation deployment, but it does not have a workflow that runs library checks for pull requests. Publishing is triggered directly from a release.

Add required CI covering:

  • JVM unit tests on every pull request.
  • :KMaP:build.
  • At least JS and WASM compilation.
  • Native compilation on macOS.
  • API compatibility validation.
  • Documentation and artifact-version consistency.

The Gradle wrapper is currently stored without its executable bit. The publish workflow invokes ./gradlew directly and can therefore fail, while the documentation workflow explicitly runs chmod +x ./gradlew.

5

Protect the published API

KMaP is publicly published but does not currently keep an API dump or enable explicit API mode. Add Kotlin binary compatibility validation and review API changes as part of CI.

This is particularly important for public data classes such as CameraState, because adding constructor properties later can break binary compatibility. Kotlin's official guidance recommends API validation and explicit return types for library APIs. See the Kotlin library compatibility guidelines.

6

Document the public API

Only four KDoc blocks are present in commonMain. Public types such as MapState, MotionController, coordinate reference classes, canvas parameters, and TileResult should document:

  • Units, axes, coordinate orientation, and valid ranges.
  • Valid zoom behavior and clamping.
  • Threading and coroutine expectations.
  • Tile row and column normalization.
  • Failure, retry, and cancellation semantics.
  • Whether exposed state may be mutated directly.

Generate Dokka API documentation rather than publishing an empty Javadoc jar.

7

Reduce the library dependency surface

KMaP/build.gradle.kts includes Material 3 and Compose resources, but the library source does not appear to use either dependency. Removing them would reduce consumer download size, build work, and dependency-conflict risk.

The dependency checker also reports that Compose runtime and resources version 1.11.1 cannot resolve for iosX64, although the JVM test task completes successfully. Removing unused resources or aligning target support with published artifacts would eliminate this warning.

Product-facing improvements

8

Expose observable loading and error state

TileResult.Failure contains only tile coordinates, while tile-processing exceptions are reduced to println. Consumers need structured state to build loading indicators, diagnostics, and recovery UX.

Expose:

  • Loading and idle state.
  • Per-source error events.
  • Failure reason and retryability.
  • Loaded, queued, processing, and failed tile counts.
  • An optional logger callback.
  • Camera moving and idle events.
9

Add standard map operations

High-value additions for consumers include:

  • fitBounds(...).
  • animateTo(CameraPosition).
  • Minimum and maximum camera bounds.
  • An explicit initial camera position for rememberMapState.
  • Projection and map-property presets, especially Web Mercator.
  • Tile prefetch for a region or route.
  • A snapshot or export API where platforms support it.
10

Support accessibility and attribution

The map does not expose an obvious semantics layer. Compose semantics power accessibility and UI testing; see the Compose semantics documentation.

Consider:

  • A map content description.
  • Accessible marker labels and actions.
  • Keyboard panning and zooming on Desktop and Web.
  • Focus traversal for interactive overlays.
  • A standard attribution overlay or API. Style sources already carry attribution data, but it is not surfaced by the map UI.
11

Clarify vector support

The README says vector work is paused, but vector APIs are included in the public library and documentation. Mark them explicitly experimental with @RequiresOptIn, document known limitations, or move them into a separate experimental artifact. This prevents incomplete behavior from being mistaken for stable API.

Recommended quick wins

  • Update README and MkDocs dependency examples from 0.4.1 to the published 0.4.2.
  • Store gradlew as executable.
  • Remove unused Material 3 and Compose resources dependencies.
  • Add pull-request CI that runs :KMaP:jvmTest.
  • Remove the detached SupervisorJob.
  • Bound tile concurrency and request queues.
  • Add tests for MapState, CanvasKernel, and TileRenderer.

Verification and verdict

Current result: :KMaP:jvmTest passes with 98 tests.

The build reports three Kotlin compiler warnings, Gradle deprecation warnings, and the noted iosX64 dependency-resolution warning. No critical security vulnerability stood out during the review.

Overall verdict: the primary risks are lifecycle management, unbounded resource use, correctness coverage, and public API stability. Addressing the tile pipeline and its tests first will provide the strongest foundation for subsequent features.
